# ADR-0003: Owned conversation execution context

Status: Accepted (US-09 contracts and offline direct-history execution)

Related issue: [US-09 #23](https://github.com/rafaself/atf-ai-engineer-challenge/issues/23)

## Context

Sprint 2 needs contextual conversations and secure customer operations without
coupling application interfaces to HTTP, Pydantic AI, or a persistence engine.
Public messages and model-generated arguments cannot establish customer identity.
The user approved server-side demo bearer-token mappings and explicitly chose
working direct-history execution in US-09, before persistence and HTTP sessions.

## Decision

Keep frozen Pydantic values in contracts and structural interfaces in ports:

| Value/interface | Responsibility |
| --- | --- |
| CustomerIdentity | Strict positive customer identifier supplied by a trusted caller; no credential field. |
| ConversationSession | Owner identity and a UUID4 generated by default on the server; an existing UUID4 can be restored by trusted code. |
| ConversationMessage | Nonblank text with user or assistant role; no system/tool roles or provider payloads. |
| ExecutionContext | Optional trusted identity/session and an immutable tuple of completed user/assistant pairs. |
| CustomerIdentityResolver.resolve | Credential-to-identity protocol that returns CustomerIdentity or raises AuthenticationError. |

A session requires matching trusted identity. Missing identity raises
AuthenticationError; a different owner raises the generic SessionAccessError.
Nonempty history requires an owned session and complete alternating pairs, starting
with user and ending with assistant. Malformed values remain Pydantic validation
errors. Empty context permits stateless catalog support, not customer access.

Both ChatService.chat and AgentExecutor.run require keyword-only context. The
service and concrete executor revalidate it before model execution, including
contexts assembled with Pydantic's unchecked construction API. Core modules remain
independent of HTTP, SQLite, AWS, and Pydantic AI. Identity is meaningful only when
supplied by trusted application code: constructing a value does not authenticate
anyone, check a database, or grant authority to arbitrary external Python callers.

The agent adapter builds a fresh SDK message list for every invocation. Historical
user/assistant text stays in its corresponding role; identity/session metadata,
credentials, and historical tool calls/returns are not translated. This prevents
historical tool results from driving current-run output notices. Past answers can
resolve conversational references but are not current evidence for prices/stock;
the prompt requires new retrieval. Prompts and controlled models do not establish
universal grounding or prompt-injection resistance.

The HTTP payload remains message-only with answer-only responses. The route
supplies empty context and rejects client identity, history, session, and context
fields. No compatibility shim, implicit trusted customer, or temporary session
repository is added.

Application error mappings are sanitized: AuthenticationError → 401,
SessionAccessError → 404, SessionConflictError → 409, and
ConversationPersistenceError → 500. Unknown and foreign sessions must share a
safe inaccessible-session outcome when lookup is implemented. These mappings
prepare US-10; the current HTTP implementation does not resolve sessions.

## Consequences and handoff

Trusted non-HTTP callers can explicitly supply history now; service/adapter code
retains no conversation state. The caller owns authentic session provenance and
history selection. US-09 does not save turns, bound history size, validate real
credentials, check session existence, or demonstrate restart persistence.

US-10 will resolve local demo bearer tokens through a server-side mapping before
session access, create an owned session when its identifier is omitted, and return
its ID. An explicit invalid/unknown/foreign ID must never silently create a session.
It will select bounded history, persist complete successful turns atomically in a
separate SQLite database, and reject overlapping same-session turns. Identity
changes cannot reassign ownership. US-11 will validate the configured customer IDs
against imported records and add read-only order authorization. These are follow-up
requirements, not implemented behavior or production authentication.

No token parser/environment variable is introduced yet. Credentials must remain
outside context, prompts, logs, and Git. Existing opt-in diagnostics can contain
conversational text and final answers; do not supply sensitive history with logs
enabled. US-10 must replace raw content logging before persisted customer sessions.

## Validation

Contract tests first failed for missing ownership and incomplete turns; execution
tests first failed because the existing interfaces could not accept context.
Passing offline tests now cover immutable values, complete pairs, identity/owner
mismatches before model execution, independent concurrent calls, text-only SDK
translation and order, stateless HTTP input, sanitized errors, and core imports.
A controlled-model/real-SQLite integration verifies fresh catalog results and no
old selection notice replay; that integration was added after implementation, so
its failing baseline was not observed. No live multi-turn Bedrock evidence is
claimed; that remains the explicitly opted-in US-13 evaluation.
